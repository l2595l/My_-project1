## 1. 项目目标（一句话）

在 Unity 2022.3 里做一款参考 Kards 的二战题材卡牌游戏，当前处于 **MVP 阶段：跑通核心循环（抽牌 → 资源 +1 → 出牌 → 移动 → 攻击 → 结束回合）**，玩家 vs 贪心 AI。**三条战线、HQ 单位化与疲劳机制已落地**；**兵种系统第一轮（5 种兵种 + 火炮/轰炸机的反击例外）已落地，但射程一律沿用现行规则（等价于"全员步兵"）**；暂时没有阵营、关键字异能、卡组构筑。

### 3.3 AI（贪心，[阶段2C] 已适配 HQ 单位与"行动费扣资源"）

`StepTurn()` 的固定顺序是 **出牌 → 攻击 → 移动**（UI 与 headless 模拟共用同一份，见 §5.1 第 5 条）：

1. **出牌**：能出就出，优先出费用最高的牌；指令卡要判断"这一手能否吃满价值"（急救只在能回满时才用、炮火覆盖只在能击杀单位时才用、**补给空投只在打出去不会爆牌时才用**）
   - **[阶段2C] 关键新增：资源预留（`ReserveForActions`）** —— 出牌前先算出"本回合还有几个没行动的单位"，为每个留 1 点资源。否则会出现**"场面很大、却一个单位都动不了"**的坐等僵局（这是"行动费与部署共用资源池"的直接副作用）
2. **攻击**（分两阶段，角色不重叠）：
   - **阶段 A · 支援线单位防守交换**：只打敌方**前线**单位（那是它们唯一够得着的目标），两轮 —— 先白吃（自己不死），再放宽到"能击杀就换"。**[阶段2.5A] 判断"自己会不会死"（`dies`）改调 `GameEngine.CounterDamage(atk, tgt)`** —— 与引擎共用同一份反击规则，AI 不再自己重算 `target.Attack`（否则"火炮免反击"会出现两个真相来源）
   - **阶段 B · 前线单位打脸**：前线单位的默认动作是**直接攻击 HQ**，不参与交换
3. **移动**：每回合至多移一个单位上前线。**前线归我方时也继续增援**（不能只占一个就走），选人用**血量优先**（`Health * 2 + Attack`）

> **[阶段2C] 一处必须记住的过滤**：AI 的攻击/移动枚举都走 `CollectUnitsOf`，
> 它**已把 HQ 滤掉**（HQ 不是可作战单位）。所以 AI 不会去"移动 HQ"或"让 HQ 攻击"，
> 也不需要自己补 `if (IsHq) continue;`。

> **为什么顺序是"先攻击再移动"**：移动会先把资源花掉（一个 6 费单位移上前线要 3 点），
> 于是"已经站在前线、本该打 HQ 的单位"整回合都动不了。这是第一版实测里 L1（击破 HQ）= 0 的直接原因。
>
> **为什么前线单位不打交换而是打脸**：如果前线单位也去交换，双方会在中线上无限对耗，
> 20 点 HQ 一点都掉不下来（L1 = 0，胜负全靠牌库抽空，先手胜率飙到 93%）。
> "支援线负责清场、前线负责输出"这条分工是 200 局实测逼出来的。

## 5. 关键设计约定（必须遵守）

### 5.1 架构分层

```
      ┌──────────────────────────────────────┐
      │ View（Assembly-CSharp）              │
      │  UiKit / CardView / GamePresenter    │
      │  · 只读 GameState                    │
      │  · 只通过 GameEngine 的公开方法改状态 │
      └───────────────┬──────────────────────┘
                      │ 单向依赖
      ┌───────────────▼──────────────────────┐
      │ Core（KardsLike.Core，无 Unity 依赖） │
      │  Rng / CardDb / GameState / GameEngine│
      └──────────────────────────────────────┘
```

**六条硬约束**：

1. **Core 目录下的代码不得 `using UnityEngine`。** asmdef 已经设了 `"noEngineReferences": true`，违反会直接编译报错——这是结构性保证，不靠自觉。
2. **渲染层绝不回写状态。** UI 可以在任何时候被整个销毁重建，对局不受影响。当前刷新策略是"全量重建卡牌"（三线 + 手牌，最多约 30 个对象），换取"界面永远等于状态"这条不变量。
3. **随机数只用 `Rng`，禁止 `UnityEngine.Random` / `System.Random`。** 同一 seed 的对局必须逐步可复现。
4. **加卡只改 `CardDb.Cards`。** 如果加一张新卡需要动 `GameEngine`，说明抽象漏了。
5. **规则正确性落在引擎，UI 不持有规则**（2026-10-08 新增）。UI 只负责画出来、把引擎给的拒绝原因显示出来。**判断标准：某条规则只写在 `GamePresenter` 里而引擎不知道，就是错的。** 反面教材是已修掉的 F2（精准打击目标归属）。
6. **公开操作自带回合归属守卫**（2026-10-08 新增）。`EndTurn` / `PlayCard` / `AttackWithUnit` 自己校验能不能执行，不指望调用方先调 `CanInteract()`。`MatchMode.AiVsAi` 下守卫完全关闭（阶段 4 需要）。

### 5.2 命名规范

- 卡牌 id：`unit_xxx` / `order_xxx`，全小写下划线。**一旦发布不可更改**（日志与统计靠它）。
- C# 字段：私有 `_camelCase`，公开 `PascalCase`（符合 Unity 惯例）。
- 常量放在所属类的顶部，带 XML 注释说明来源章节。
- 所有注释用中文；提及规则时标注《阶段0-设计文档.md》的章节号。

### 5.3 数值口径

- 单位卡面板预算：`攻击 + 生命 = 2 × 费用 + 1`
- 费用范围 1~6；资源上限 10；**HQ 20 血（`HqStartingHealth`）**；手牌上限 10
- **[阶段2B] 两条线的容量**：支援阵线 **5**（每人独占，`SupportLineCapacity`，**[阶段2C] 含 HQ ⇒ 最多再放 4 个单位**）；前线 **5**（双方共用，`FrontlineCapacity`）
  · **[阶段2.5 提交B] 4 已改回 Kards 口径的 5**（拍板项 ①，2026-10-08，提交 `4ac65f98`）—— 唯一逻辑改动就这一个常量；View 无需改（`BuildSupportPanelCards` 按 `SupportLine.Count` 动态居中）
  —— 旧的"战场上限 7"已删除（那是"一行放得下 7 张"的 UI 推导，三行之后"一行"不再唯一）
- **[阶段2C] 行动费**：按部署费用分档 **1~2 费 → 1 点 / 3~4 费 → 2 点 / 5~6 费 → 3 点**，
  **从资源池扣**（与部署共用 `Resources`）；**没有独立的行动点资源**（`ActionPoints` 已删除）
  · **[阶段2.5A] 数据源已字段化**：唯一真相 = `CardDef.ActionCost`；`CardDb.ExpectedActionCost(cost)` 只作校验基准；
    `GameEngine.ActionCostOf(card)` 退化为**一行取值**。**档位逻辑不得再出现在结算路径上**（否则卡面与引擎会分家）

### 5.4 字体与编码（踩过的坑）

- `.cs` 文件必须存成 **UTF-8 with BOM**。中文 Windows 上无 BOM 会被按 GBK 解析，中文注释和字符串全部乱码。批量转换脚本见本文档 §7。
- TMP 字体是**动态字体资源**（`AtlasPopulationMode.Dynamic`），字形按需加入图集，不要改成静态模式，否则中文会缺字。
- `TMP_Settings.defaultFontAsset` 已指向 SimHei SDF，`UiKit.Font` 还会额外从 Resources 加载一次作为双保险。

### 5.5 Unity 使用注意

- **Unity 窗口不在前台时游戏循环不推进**（`Time.frameCount` 不增长），协程里的 `WaitForSeconds` 会卡住。调试 AI 回合时如果发现"卡住不动"，先确认窗口在前台、`EditorApplication.isPaused == false`。
- 上一条的推论（2026-10-08 实测）：**窗口不聚焦时 60 秒倒计时也几乎不走**（干等 3 秒只推进了 0.02 秒）。所以验证倒计时**不要靠"干等 60 秒"** —— 改用 `T` 键开关，或反射把 `_turnTimeLeft` 压低后再调一次 `UpdateTimerVisual()`；要触发归零就调一次 `TickTurnTimer(1.5f)`。
- 屏幕适配用的是**设计画框**方案：界面搭在固定 1920×1080 的 `DesignFrame` 上，按 `min(屏宽/1920, 屏高/1080)` 等比缩放居中。**不要**改回 `CanvasScaler.ScaleWithScreenSize`——那套在非 16:9 窗口下会让左右元素和中间手牌重叠。
- **[2026-10-08 实操总结] 在编辑器里用脚本驱动 UI 测试的正确姿势**（这四条是连续踩出来的）：
  1. **`EditorApplication.Step()` 能让循环前进**，即使窗口不在前台。进 Play 后 UI 没建出来的话，调它几次即可（`KardsCanvas` 是在 `GamePresenter.Start()` 里运行时创建的）。
  2. **`Object.Destroy` 到帧末才生效**。先 `SetActive(false)` 再 `Destroy` 的记账式重建（`GameLayout.ClearSpawned`）在**帧不推进时**会让旧对象一直留在 hierarchy 里（`HandRow` 会堆积到十几个 `Card`）。它们已 inactive、不渲染，**不是泄漏**；但要按"active 的子物体才是当前帧的卡"来取。
  3. **`RestartGame()` 会替换 `_engine` 对象**。如果先缓存了引擎引用再重开，拿到的是**旧引擎**（会看到 `HalfTurn` 莫名很大）。重开后必须重新取。
  4. **模拟点击要走 `Button.onClick.Invoke()`**，不要反射调 `GameInteraction` —— 前者连"事件绑定是否正确"一起验了。注意 `GetPersistentEventCount()` 对运行时 `AddListener` 永远是 0，不代表没绑上。

### 改动前必做：git 基线提交（2026-10-08 起）

重构或大改之前先存一个快照，改完用 `git diff` 直接证明"到底改了哪些文件、多了少了几行"。
这样就不再需要每次现编一套手工指纹（数成员定义、数 `AddLog` 调用点、比常量字面量……）。

```bash
# 1. 动手前 —— 存快照
git add -A && git commit -m "重构前快照"

# 2. 改代码 …

# 3. 看改了哪些文件、多了少了几行（摘要）
git diff --stat

# 4. 逐行看（-M 识别"整段搬家"，-w 忽略纯空白变动）
git diff -M -w

# 5. 改坏了立刻整体回退（也可只退单个文件）
git checkout -- Assets/KardsLike/Scripts/Core/GameEngine.Combat.cs
```

**边界必须清楚：git 只证明"文本层改了什么"，证明不了"行为没变"。**
行为层仍必须靠 **自检 9/9 + 200 局逐位一致（同种子、同统计、日志条数 200）**。
两者互补 —— git 负责"改动范围可证"，模拟与自检负责"规则行为未变"，不能互相替代。
