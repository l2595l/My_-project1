### Q2 · "不受反击"加在攻击者身上还是目标身上？用 `AttackWithUnit` 里的哪两个变量表达？

**加在"双方各自的角色"上，不是加在某一方身上** —— 这正是它容易写错的地方。

现有代码只有两个变量：

```csharp
int damageToTarget   = attacker.Attack;   // ① 主动攻击伤害：攻击者打给目标的
int damageToAttacker = target.Attack;     // ② 反击伤害：目标的攻击力回敬给攻击者的
```

要表达的规则是：

| 谁的兵种 | 影响哪个变量 | 为什么 |
|---|---|---|
| 攻击者是**火炮** | ② → **0** | 火炮不受反击 |
| 攻击者是**轰炸机** | ② → **0** | 轰炸机不承受反击 |
| **目标**是**轰炸机** | ② → **0** | 轰炸机不造成反击（它不还手）|
| 攻击者是**战斗机** / 步兵 / 坦克 | ② 不变 | 正常双向结算 |
| **目标**是**火炮** | ② 不变 | 火炮**照常反击**（它只是"不受"，不是"不造成"）|

⇒ **三个兵种规则全部收口到同一个变量 ②**，① 永远不变。
这就是为什么它必须是一个独立方法：如果散在多个 `if` 里，最容易写成"轰炸机当攻击者时免反击、当目标时忘了免"，两边行为不一致。

**关于"轰炸机打战斗机"这条例外 —— ✅ 已于提交 C 按原文敲定落地（本条原判断已翻案）：**

⚠️ **本节初稿记错了原文，据此推出的"主语歧义"并不存在。** 初稿记的是
"轰炸机……既不承受也不造成反击（**被战斗机攻击时例外，会承受**）"，然后论证：
字面读作"轰炸机承受"，但战斗里"承受反击"的固定角色是攻击者 ⇒ 歧义 ⇒ 不猜。**这一步是错的。**

**提交 C 重新核对的原文（中文维基 Kards 条目，与 §9.1 登记时同类来源）：**

> 「轰炸机在攻击时不会受到反击伤害（**除非攻击目标是战斗机**），能够无视"被守护"状态，
> 但在被攻击时也不会造成反击伤害。」

例外挂在**"攻击目标是战斗机"**上 —— 主语是**轰炸机（作为攻击者）**，不是战斗机。**没有歧义。**

交叉印证（三个来源结论一致）：

| 来源 | 原话要点 |
|---|---|
| 中文维基 Kards 条目 | 「轰炸机在攻击时不会受到反击伤害（**除非攻击目标是战斗机**）」 |
| KARDS Fandom · Tips | 「…and **it's the only time bombers can take damage in return when attacking**」 |
| LevelWinner 新手指南 | 「bombers **do not take counterattack damage**」+「bombers **do not deal counterattack damage**」 |

**用户 2026-10-08 拍板：按该原文实现**（见设计文档 §12.2）。落地后的完整矩阵：

| 场景 | 谁掉血 |
|---|---|
| 轰炸机 → 非战斗机 | 只有目标掉血（轰炸机攻击时不受反击） |
| **轰炸机 → 战斗机** | **双方都掉血**（例外） |
| 任何单位 → 轰炸机 | 只有轰炸机掉血（它被攻击时也**不还手**） |
| 战斗机 → 轰炸机 | 只有轰炸机掉血（**不是**"战斗机打轰炸机时轰炸机还手"） |

> ⚠️ **对称性提醒**：初稿的三种口径 (A)(B)(C) 里，(A)(B) 都假设"战斗机打轰炸机时轰炸机还手" ——
> **那个方向本来就是错的**。真正的例外在**反方向**。这正是"记错机制 → 据此论证"的第三次复发
> （前两次是 OPS 与召唤失调），教训同前：**引用参考作品的机制前必须核原文，且要核到原句。**

> ⚠️ **实现顺序有意义**：`CounterDamage` 必须先判目标是轰炸机（⇒ 0），再判攻击者。
> 否则「战斗机打轰炸机」会落到底部的 `return target.Attack;`，把轰炸机 4 点攻击当反击打回去。
> 该 bug **只在"战斗机打轰炸机"这一种组合下出现**，200 局抽样发现不了 ——
> 自检第 9 项专门加了第 8 条来钉住它（见设计文档 §12.2）。

### Q5 · 我方轰炸机攻击敌方 HQ，攻击者掉血吗？

**不掉**，且**有两条各自独立的理由**同时指向这个结果：

1. HQ 攻击力是 **0**（数值保证，"打 HQ 不被反击"从来不需要特判）
2. 轰炸机**不承受**反击

⇒ `damageToAttacker = 0`。两条理由叠加，所以这一条**不能**用来单独证明"轰炸机免反击"生效了 ——
自检第 9 项因此必须另外用"步兵/坦克打 HQ"做**对照**（那个也掉 0 血，但原因只有第 1 条），
再用"轰炸机打**普通单位**"来证明第 2 条真的起作用。

> 这是一条容易自我欺骗的验证陷阱：如果只测"轰炸机打 HQ 不掉血"，那么"轰炸机免反击根本没实现"也会通过。

### Q6 · AI 的"先白吃 / 再能击杀就换"判据必须怎么改？不改有什么后果？

现在 `GreedyAI.AttackPhase()` 里是这样判的：

```csharp
bool kills = atk.Attack >= tgt.Health;
if (!kills) continue;
bool dies = tgt.Attack >= atk.Health;   // ← AI 自己假设"目标一定会反击"
if (requireNoLoss && dies) continue;    // ← 第一轮只做白吃交换
```

**`dies` 是 AI 自己算的，不经过引擎。** 改兵种之后它就错了：

- 攻击者是**火炮 / 轰炸机**时，`dies` 恒为 `false`（不吃反击），
  但代码会算出 `true` ⇒ AI **以为会亏，于是放弃必杀的交换**
- 后果一：新机制在 AI 对局里**几乎不生效** ⇒ 200 局测不出真实影响（测试失效）
- 后果二：人类玩家白占便宜（AI 不用人类能用的规则）⇒ 严重时先手/后手偏差的归因全错

**改法：`dies` 必须走与引擎结算**同一个**出口**，不能 AI 自己猜。**

```csharp
bool dies = GameEngine.CounterDamage(atk, tgt) >= atk.Health;
```

⚠️ **这里我故意偏离了提示词 2 的一句话。** 提示词说 `ResolveCounterDamage` 做成**私有**方法；
但私有 = AI 用不到 = AI 只能把 `tgt.Attack` 那份逻辑再抄一遍 = **规则出现两个真相来源**，
正是本项目已经踩过两次的坑（F2 精准打击归属、F6 召唤失调），也正是这次要做"行动费字段化"的原因。

所以实现为 **`internal static int CounterDamage(UnitInstance attacker, UnitInstance target)`**（纯函数、无状态）：
引擎结算与 AI 预测**共用同一个函数**，而 `internal` 保证 View 层用不到它（与既有约定一致 ——
`BeginAiTurn` / `EndAiTurn` 就是 `internal`）。
⇒ 本轮**没有**改动 AI 的策略结构、评分公式与动作顺序，只把 `dies` 的数据来源换成引擎。

### Q7 · 自检第 5 项（部署失调 + 每回合一次行动）会受影响吗？第 7 项（三线与行动费）呢？

| 项 | 会不会受影响 | 原因 |
|---|---|---|
| **第 5 项** | **不受影响** | 它用一个**真实开局手牌**里的单位卡做用例（只会是 1~2 费卡，即侦察兵 / 步兵班 / 机枪阵地，**全是步兵**），步兵双向结算 ⇒ 反击规则不介入；行动费通过 `ActionCostOf` 读取，字段化后值不变 |
| **第 7 项** | **不受本轮影响，但会被拍板项 ① 影响** | 它断言的 `supportCount == GameEngine.SupportLineCapacity` 是**从常量推导**的，改常量会自动跟着变；但报告里有一句**硬编码文案**「HQ 占一格 ⇒ 除 HQ 外只能放 3 个」，① 落地后必须改成 `SupportLineCapacity - 1` |

⇒ **本轮的改动不会让这两项失败**；① 落地时需要顺手修那句硬编码文案（已列为 §4 的检查项）。

### Q8 · 行动费字段化之后，"按部署费用分 1/2/3 档"这条**规则**要不要保留？谁来校验？

**要保留。** 它是一条**数值设计规则**，不是实现细节：

- 它的作用是保证"费用已经编码了强度"（面板预算 = 2 × 费用 + 1）这条口径有对应物
- 它让 10 点资源上限下的取舍成立（5~6 费的大哥要 3 点才能动，等于"打大牌还是多动一次"）

**约束**：`CardDef.ActionCost` 必须等于档位函数的期望值。

**校验者**：`CardDb.ValidatePanelBudget()` 扩展为校验三条（提示词要求），由自检第 1 项调用。
档位函数本身留在 **`CardDb.ExpectedActionCost(int deployCost)`** 作为**基准**。

⇒ 于是"两个真相来源"被改造成 **"一份数据 + 一个校验器"**：

| 位置 | 角色 | 谁能调 |
|---|---|---|
| `CardDef.ActionCost` | **唯一数据源**，结算就读它 | 引擎 / 卡面都读它 |
| `CardDb.ExpectedActionCost()` | **期望值基准**，只用于校验 | 只有 `CardDb` 与自检 |
| `GameEngine.ActionCostOf()` | 退化为一行 `return card.ActionCost` | 结算路径的唯一出口 |

⚠️ 关键：**档位函数不得再出现在任何结算路径上**。引擎里一旦残留一份"再算一遍"的逻辑，
卡面显示与引擎扣费就可能不一致 —— 那正是这次字段化要消灭的东西。

### Q9 · 预计本轮让对局变长还是变短？"堆大哥"会变强吗？

**先纠正问题里的一处错误**：问题问"**榴弹炮、重型坦克**拿到'免反击'会不会让'堆大哥'变强" ——
但按 Q1 的分配，**重型坦克是「坦克」，它不拿免反击**。本轮拿到"免反击"的**只有榴弹炮一张卡**。

修正后的预测（可证伪）：

1. **只有 12 张卡里的 1 张（榴弹炮）行为发生变化** ⇒ 大多数对局的随机序列不变 ⇒
   **预计 200 局里只有少数几局（< 25 局）的终局与长度发生变化**。
   ⚠️ 这是一条**强预测**：如果 200 局大面积改变，说明我改错了地方（比如把坦克也写成了免反击），必须回头查。
2. **平均 HalfTurn 预计略降或基本持平**：榴弹炮的 6 攻现在能"白吃"5 血以内的任何单位，
   它落地后清场效率上升 ⇒ 战局更容易被推动；但它 5 费、上前线还要 3 点行动费，
   出场窗口本来就晚。
3. **先手偏差预计微升（可能从 7.0 到 8~11 个百分点）**：
   "谁先到 5 资源"是有先手优势的，而 5 费最强的牌（榴弹炮）变强会放大这份优势。
   若偏差反而下降，则说明这 1 张卡的影响被摊薄了 —— 同样是有信息量的结果。
4. **"堆大哥"结论**：变的不是"大哥们"，是**一张 5 费解场牌**。
   真正的"堆大哥"风险在任务 D —— 越线射程会让火炮 / 飞机不必上前线就能打脸，
   那才动摇"抢前线是打 HQ 唯一陆路"这条支柱。
   **本轮不会出现这个问题**（R6 钉死了射程）。

## 3. 三个拍板项的连带影响（拍板之后才浮现的东西）

### 3.1 拍板项 ①「支援阵线容量 4 → 5」的连带面

改成 5（含 HQ ⇒ 可再放 4 个单位）只改一个常量，但它牵动 4 处：

| 牵连点 | 说明 |
|---|---|
| `GameEngine.SupportLineCapacity` | 4 → 5，唯一改动点 |
| `GameState.IsSupportLineFull` / `GameEngine.CanPlayCard` 的拒绝文案 | 都从常量推导，自动跟随 ✅ |
| **自检第 7 项的报告文案** | 「除 HQ 外只能放 3 个」是**硬编码**的 ⇒ 必须改成由常量推导（否则报告会说谎）|
| **View 的支援线排布** | `GameLayout.PlayerSupportRow` 是固定 **1120 px** 宽的行；战场卡 112 px ⇒ 4 张 = 448 px、5 张 = 560 px，**横向放得下**。但需实机确认排布容器（LayoutGroup）自动重排，不能只看数字 |

⚠️ **平衡影响不可忽略**：支援线是"铺场与保命共用同一份空间"。从 4 增到 5
等于给双方各多一格，双方对等 ⇒ 预计不改变先手偏差的方向，但会**提高场面密度、拉长对局**。
必须单独一轮 200 局。

### 3.2 拍板项 ③「新增两卡 + 牌库 36 → 42」撞上了一个硬约束 ⚠️

这是拍板之后才算出来的，**提示词 2 写的时候没有覆盖**：

**加两张卡 ⇒ 卡池 12 → 14 ⇒ 牌库 = 14 × 3 = 42 张。而 `MaxTurns = 72` 是按 36 张算出来的。**

推导（先手视角，**忽略额外抽牌**，所以这是自然终止点的**下界**）：

```
牌库 D 张，起手 4 张从牌库扣 ⇒ 余 D−4
先手第一个回合不抽牌 ⇒ 它的第 n 个回合结束时共抽了 (n−1) 张
牌库空 ⇒ n − 1 = D − 4 ⇒ n = D − 3

牌库空之后开始吃疲劳，2+4+8+16 = 30 > 20 ⇒ 再撑 4 个自己的回合
⇒ 最后一个己方回合 n = (D − 3) + 3 = D
⇒ 先手需要的半回合数 = 2D − 1
```

| 牌库 D | 自然终止点（HalfTurn） | `MaxTurns = 72` 够吗 |
|---|---|---|
| **36（现状）** | 2×36 − 1 = **71** | 够，但**余量只剩 1 个半回合** |
| **42（③ 之后）** | 2×42 − 1 = **83** | ❌ **不够** ⇒ L3 会在疲劳结算完之前抢跑，把「L3 触发 0 局」这条性质打破 |

**⇒ 拍板项 ③ 必须连带把 `MaxTurns` 从 72 提到至少 83；建议取 88（= 2D + 4，留 5 个半回合余量）。**

这也解释了为什么现状是"刚好够"：36 张 + 疲劳 4 次 = 71，离 72 只差 1。
（实际对局里 `补给空投` 会额外抽牌，所以真正的牌库空得更早、余量比公式更大 ——
但**不能靠这个巧合**，`MaxTurns` 必须按最坏情况算。）

### 3.3 拍板项 ②「兵种拆两轮」

与提示词 2 的划分一致，无新增影响。本轮 = 第一轮（字段 + 反击例外 + 行动费字段化），
越线射程 + 战斗机拦截 = 任务 D。

## 6. 实测结果：§2-Q9 的预测**被证伪了**（2026-10-08 补记）

写完 §2-Q9 之后本轮已经落地并实跑，结果如下。**这条必须留下，不能悄悄改掉 Q9。**

### 6.1 数字

| 指标 | v1.6 基线 | 本轮实测 | 我的预测 | 判定 |
|---|---|---|---|---|
| 先手胜 | 107（53.5%） | **105（52.5%）** | 微升到 8~11 个百分点偏差 | ❌ 实际偏差 **→5.0**（下降） |
| 终局构成 | 打脸 174 / 疲劳 26 | **打脸 187 / 疲劳 13** | "只有少数几局（< 25 局）变化" | ❌ 实际 **30 局**换了终局类型 |
| 平均 HalfTurn | 40.28 | **37.73** | 略降或持平 | ⭕ 方向对，幅度低估 |
| 最大 HalfTurn | 59 | **58** | — | — |
| L3 触发 | 0 | **0** | 0 | ✅ |
| seed=12345 | Player0Win / 58 / 9 : −15 / 200 条日志 | **Player1Win / 28 / −5 : 18 / 98 条日志** | — | 面目全非 |

### 6.2 错在哪

**我以为"只有 12 张卡里的 1 张变了 ⇒ 只有少数几局会变"。这个推理漏了一层：对局是确定性混沌的。**

- 榴弹炮在牌库里有 **3 份**；一局平均约 19 次抽牌，其中至少摸到一张的概率约 **90%**
- `GreedyAI` 是**确定性**贪心：一次决策变化（"这次交换我会不会死"的答案变了）
  会把整局的动作序列彻底岔开，后续每一步的输入都不同
- ⇒ 变化的不是"1/12 的对局"，而是"**摸到过那张卡的所有对局**"

**教训（写进方法库）：不能用"只有 1/N 张卡变了"去推断"只有 1/N 的对局会变"。**
在确定性 + 混沌的模拟里，**任何一个规则的改动都可能污染绝大多数对局**，
所以"改动是否只落在该落的地方"**不能靠预测**，必须靠 §6.3 那种对照实验。

### 6.3 归因是怎么证明的（这比预测重要）

**对照实验**：把榴弹炮的兵种**临时改回 `UnitType.Infantry`**（= 取消火炮例外），重跑自检。

| 指标 | v1.6 基线 | 临时改回步兵 | 本轮（火炮例外生效） |
|---|---|---|---|
| 先手胜 | 107（53.5%） | **107（53.5%）** | 105（52.5%） |
| 后手胜 | 93 | **93** | 95 |
| 打脸击破 HQ | 174 | **174** | 187 |
| 疲劳击破 HQ | 26 | **26** | 13 |
| L3 | 0 | **0** | 0 |
| 平均 HalfTurn | 40.28 | **40.28** | 37.73 |
| 最大 HalfTurn | 59 | **59** | 58 |
| seed=12345 | Player0Win / 58 / 9 : −15 / **200 条日志** | **逐项一致** | Player1Win / 28 / −5 : 18 / 98 条日志 |

⇒ **逐位一致。** 于是可以下这个结论：

> 兵种字段、行动费字段化、`ActionCostOf` 退化为取值、`CounterDamage` 收口、AI 换数据源
> —— 这五项**结构性改动在"没有火炮"的状态下行为完全不变（200 局逐位一致）**；
> 200 局的**全部差异 100% 可归因到"榴弹炮获得免反击"这一条规则**。

**这才是"改动范围可证"的正确做法**：与其预测影响面，不如造一个"关掉新规则"的对照，
用逐位一致来证明其余的改动是零副作用的。它比任何"我检查过了"都硬。

### 6.4 变化方向的解释（不是异常）

打脸终局 **+13** 与疲劳终局 **−13** **恰好抵消** —— 这与"榴弹炮（6 攻）不再自损
⇒ 清场与推进能力上升 ⇒ 对局更早由 HQ 归零结束，而不是被拖到双方牌库抽干"完全自洽。
平均 HalfTurn 缩短 2.55 是同一件事的另一个表现。

⚠️ 但**不要**据此说"火炮对先手有利/不利" —— 先手偏差从 7.0 降到 5.0 只有 2 局的量级，
**属噪声，不足以支撑任何结论**。

### 6.5 顺带确认的边界

- **`MaxTurns` 的余量仍为正，但已经很紧**：36 张牌库 + 4 次疲劳的自然终止点上界 = `2×36 − 1 = 71`，
  `MaxTurns = 72` ⇒ **余量 1 个半回合**。这正是拍板项 ③（牌库 → 42）**必须连带把 `MaxTurns` 提到 88** 的原因。
- 本轮**没有**改攻击射程：支援线单位仍然只够得着敌方前线单位（自检第 7 项 7.1 节 ✅ 证明了这一点）。
