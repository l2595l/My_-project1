## 2. 逐条回应你的 4 个问题

### 2.1 问题 1「步兵攻击敌方，自己不受伤」→ 规则已实现，问题是**看不见**

引擎没问题（§1.1 三场景实测）。真正的原因全在表现层：

- 攻击是**瞬间结算 + 全量重建卡牌**，没有任何过程
- 没有伤害数字、没有闪白、没有抖动、没有攻击方向提示
- 攻击前也**没有任何预览** —— 你只有在打完之后，靠对比两张卡的小血量徽章和细血条才能发现"哦，我也掉血了"

**修复方向（两条一起做才有效）**

| 优先级 | 做法 | 为什么 |
|---|---|---|
| **最高** | **双向伤害飘字**：结算后攻击者与目标各弹一个红色伤害数字 + 卡牌抖动 | 直接补上"挨打"的感知 |
| **高** | **攻击预览**：选中攻击者后，把"我打它 X 点 / 它反我 Y 点"直接画在两张卡上 | 比飘字更早解决问题 —— 点下去**之前**就知道会被反杀 |

> 附注：Kards 的拖拽攻击就是实时显示预期伤害的，这是它"打起来看得懂"的关键，不是特效炫。

### 2.2 问题 2「行动花费没标在左上角 + 卡牌没分兵种」

#### 2.2.1 行动花费：Kards 官方原文

> 「**行动花费** 单位的指挥点字段中字体较小的数字为单位的行动花费。**单位在部署后将仅会显示此数字。**」
> —— `kards.com/zh/how-to-play`

也就是说 Kards 的**同一个左上角位置有两种状态**：

| 状态 | 显示内容 |
|---|---|
| 在手牌里 | **部署费用（大数字）** + **行动花费（小数字）** |
| 部署到战场后 | **只显示行动花费**（部署费用不再显示） |

当前工程的差距：

| 位置 | Kards | 当前工程 | 差距 |
|---|---|---|---|
| 手牌卡左上角 | 部署费（大）+ 行动费（小） | 只有部署费 | **缺行动费** |
| 战场单位左上角 | 只有行动费 | **什么都没有** | **全缺** |

#### 2.2.2 ⚠️ 一条比 UI 本身更重要的架构发现

现在行动费是 `GameEngine.ActionCostOf(CardDef)` **算出来的**：

```
1~2 费 → 1 点 ／ 3~4 费 → 2 点 ／ 5~6 费 → 3 点
```

**卡面要显示它，就只能把这份档位逻辑在 View 里再抄一遍** —— 那就是"规则有两个真相来源"，
正是本项目已经踩过两次的坑（F2「精准打击归属」、F6「召唤失调」）。

**正确做法**：把 `ActionCost` 变成 `CardDef` 上的**显式数据字段**（写在 `CardDb` 里），
`ActionCostOf` 退化成一行取值。这样卡面直接读 `def.ActionCost`，引擎与 UI **不可能**不一致，
同时也满足"卡牌数值只存 `CardDb`"这条硬约束。

#### 2.2.3 兵种：Kards 有 5 种，当前工程一种都没有

官方口径（中/英/百科三源交叉核对一致）：

| 兵种 | 攻击射程 | 反击 | 特殊能力 |
|---|---|---|---|
| **步兵** | 只能打**相邻战线** | 造成 + 承受 | 无（基准兵种） |
| **坦克** | 只能打**相邻战线** | 造成 + 承受 | **同一回合可移动 + 攻击**（顺序不限） |
| **火炮** | **任意战线** | **不承受**反击 | 无视「守护」；血量普遍偏低 |
| **战斗机** | **任意战线**（陆+空） | 造成 + **承受** | **阻止敌方轰炸机攻击同一战线的其他目标**（拦截） |
| **轰炸机** | **任意战线** | **既不承受、也不造成**反击（被战斗机攻击时例外，会承受） | 无视「守护」；**不能攻击有敌方战斗机的战线** |

> ⚠️ 事实标注：官方 how-to-play 明确写出的只有「火炮/轰炸机**不受**反击」与「轰炸机防御时**不造成**伤害」；
> 表中其余细节（火炮反击时仍造成伤害、战斗机正常双向结算）来自百科/二手攻略交叉核对，属**推断**。
> 落地前若仍有疑问，以官方原文为准 —— 本项目已因"把参考作品记错再据此论证"栽过两次。

### 2.3 问题 3「卡牌打出没有动画」

你的观察是对的。Kards 的指令卡确实是"**在牌桌中线偏左放大展示约 1 秒 → 向左滑出屏幕**"，
且**不论谁打出都完全一样**。补齐几条你可能需要的细节：

| 动作 | Kards 表现 | 建议实现 |
|---|---|---|
| 指令打出 | 手牌位置放大 → 中线偏左展示 ~1.0s → 向**左**滑出 | View 层新增浮层，协程驱动，全场唯一实例 |
| 单位移动 | 沿格位**平移**到目标格（有过程，不是瞬移） | 位置插值 ~0.25s（SmoothStep） |
| 攻击 | 按兵种不同 | 见下表 |
| 伤害 | **双向**数字 | 双方各弹伤害数字（这条最要紧） |

兵种差异化攻击特效：

| 兵种 | 特效建议 |
|---|---|
| 步兵 | 短促突刺（冲向目标再弹回）+ 小火花 |
| 坦克 | 直线推进 + 炮口闪光 + 轻震屏 |
| 火炮 | 屏幕外抛物线弹道 → 目标处爆炸圈 |
| 战斗机 | 斜向俯冲扫掠 + 弹道线 |
| 轰炸机 | 高空投弹 + 大范围爆炸 + 强震屏 |
| **反击** | **不论兵种都要有**：防守方对攻击者弹出伤害数字 |

**三条硬约束（违反任何一条都会毁掉阶段 4）**

1. **动画只在 View 层，`Core` 一个字都不改。** `asmdef` 的 `noEngineReferences` 会直接编译报错 —— 这是好事。
2. **先结算、后播放。** 引擎状态在动画开始前就已经改完，动画只是"把刚发生的事演一遍"。
   **绝不允许动画阻塞 `GreedyAI.StepTurn()` 的动作序列**，否则"同种子结果完全一致"立刻失效。
3. **必须有"动画时长倍率"开关（含 0 = 关闭）。** 没有它，你以后每次改代码都要在动画里干等，调试体验会崩。

## 5. 执行顺序（按项目自己的方法论）

项目铁律是「**一次只加一个机制，先要规则再要代码**」。本次"兵种系统"一次要引入 5 种类型的能力，
**必须拆成两轮**，否则 200 局数据一变化你无法归因。

### 8.3 卡面框架：实测几何（任务 B 直接照抄，不要自己目测）

原图 626×830，四周各有 27~43px 透明留白。裁到不透明外接框 `(43,27)-(593,793)` 后：

```
卡框成品      550 × 766   比例 0.7180
插画开窗       left 5.8%  /  top 8.0%  /  width 88.5%  /  height 53.7%
开窗下方空白   占整卡高度 38.4%   ← 效果文字区 + 底部徽章行
```

**✅ 关键结论：现有卡牌尺寸一个都不用改。**

| | 卡框 | 卡牌 | 比例误差 |
|---|---|---|---|
| 手牌 | 0.7180 | **148×208** = 0.7115 | **0.9%**（肉眼不可见） |
| 战场 | 0.7180 | **112×150** = 0.7467 | 4%（可接受） |

这一点很重要：手牌行容器 `GameLayout.HandRow` 是 **1200×208**，8 张卡时已经很紧 ——
如果为了迁就卡框比例把手牌加宽到 157，手牌行就会溢出。
**所以正确做法是"把卡框拉伸到卡牌尺寸"，而不是"把卡牌改成卡框比例"。**

> ⚠️ **不需要九宫格（9-slice）。** 卡框是"整张开窗"设计 —— 圆角与金饰都必须按
> 整卡缩放才不变形，切 9 宫格反而会让四角金饰错位。直接用普通 Sprite 拉伸即可。

### 12.2 三个必须记下来的设计决定

**① 为什么必须有 `CardArt.asset`（而不是直接 `Resources.Load<Sprite>`）**

`Art/` 目录**刻意没有**叫 `Resources` —— 那是 Unity 保留目录名，会**整目录打进包体**，
而且一旦为了加载而改目录名，`CREDITS.txt` 与 §8 里所有路径登记**全部失效**。
所以用一份 `ScriptableObject`（放在 `Assets/KardsLike/Resources/CardArt.asset`）集中持有 7 个引用：

```csharp
// 资源缺失时只 LogWarning 一次，然后退回程序化绘制 —— "零资源也能跑"这条底线不丢
public static Sprite FrameOrNull();
public static Sprite IconOrNull(UnitType kind);
```

⇒ 这个模式以后接新素材可以直接复用：**美术资源留在 `Art/`（可读、可登记许可），运行期引用走 `Resources/` 的一个 `.asset`**。

**② 分层顺序 = 绘制顺序（uGUI 的铁律，必须在建节点时就定好）**

```
Halo → Base → Window → WindowFade → Illustration → Frame → (Glow) → Dim → Content
```

- `Frame` 在 `Illustration` **之后**建 ⇒ 卡框压在插画之上 ⇒ **插画不会溢出到卡框外**。
- `Content` 最后建 ⇒ 所有数字/文字/徽章压在最上面。
- **`Halo`（状态光晕）在最底下**：做法是在卡**背后**画一块 `Stretch(rt, -3f)` 的实心圆角块，四周露 3px。
  实测这比"给卡框换色"醒目得多（卡框是深灰石纹 + 金边，`Image.color` 乘法染色必须留在 0.72~1.0 才不毁金边）。

**③ 开窗几何用**量出来的**，不用目测的**

逐像素扫 alpha 得到（已写进 `CardArt` 常量，代码直接引用、不抄字面量）：

```csharp
public const float WindowLeft   = 0.0582f;   // x[32..518] / 550
public const float WindowTop    = 0.0796f;   // y[61..471] / 766
public const float WindowWidth  = 0.8855f;
public const float WindowHeight = 0.5366f;
public const float CornerRadius = 0.0436f;   // 24 / 550
```

两条靠实测才发现的**对齐容错**做法：

- **底色块四周各大 3px**（`w*WindowLeft - 3` / `ww + 6`）—— 多出来的部分被卡框实心区盖住，
  于是"底色与开窗的接缝"永远不会露出来，对齐误差全被吸收。
- **底色块圆角必须 ≥ 卡框圆角**（`w * CornerRadius + 2`），否则四角会露出底色的尖角。

### 13.1 本轮唯一重要的设计决定：伤害数字**不在 View 里算**

提示词要求"数字取本次各自实际扣掉的血"，而且明确列了两条特例：

> · 反击为 0 时（打 HQ、火炮 / 轰炸机免反击）**不弹攻击者的数字**

最直觉的做法是"在播放动画的地方按兵种算一遍反击伤害"，但那正是本项目**已经栽过两次**的坑
（F2 的"精准打击只能打敌方"、任务 A 的"反击伤害两个真相来源"）——
`CounterDamage` 的四条判定会被抄第二遍，而且**方向错一次就只有一种组合能暴露**（上一轮刚踩过）。

所以这里换了一条完全不同的路：**比较前后两帧的 HP**。

```
引擎把状态改完（"先结算、后播放"，硬约束 2）
        ↓
GamePresenter.Refresh() 开头：把当前场上每个单位的 Health 存成快照
        ↓
与"上一帧的快照"相减 ⇒ 谁掉了多少血 ⇒ 这就是这一次的伤害事件
```

于是三条要求**全部由构造保证，一条判断都不用写**：

| 要求 | 为什么自动成立 |
|---|---|
| 攻击后**双方**各弹一个 | 双向结算 ⇒ 两张卡的血都少了 ⇒ 两个事件 |
| 反击为 0 时不弹攻击者的数字 | 攻击者的血**根本没变** ⇒ 差值 0 ⇒ 没有事件 |
| 打 HQ 时只有 HQ 弹 | 同上（HQ 攻 0） |
| 阵亡单位也要弹 | "上一帧还在、这一帧不见了" ⇒ 掉血量 = 它当时的血 |

> 这正是本项目那条铁律的又一次应用：**UI 只读引擎的结论，绝不重算规则。**
> 换来的好处是：以后加「重甲」「烟幕」这类改变伤害的异能时，**这个文件一行都不用改**。

### 13.3 两个必须记下来的实现要点

**① 飘字为什么不会被"整卡重建"带走**

`Refresh()` 的策略是**全量重建**（`ClearSpawned()` 销毁所有卡）。飘字若挂在卡上，
AI 回合每 0.4 秒一次的刷新会把 0.6 秒的飘字腰斩。

硬约束 2 要求"动画不得阻塞 `GreedyAI.StepTurn()`"。本轮的做法是：**一步都不新增 `yield`**，
飘字与抖动都是独立协程，与 AI 那 0.4 秒的步进间隔**重叠播放**。
单步感知时长 = max(0.4, 0.6) = **0.6 秒** ≪ 提示词给的 2 秒上限。

**② 全场唯一实例（原文 §2.3 的口径）** —— 用 `Queue<CardDef>` 排队，一张播完再播下一张。
连续打出两张时实测**同时存在最多 1 张**。
⚠️ 队列跑空时**必须把 `_orderRoutine` 置空**，否则第一次之后再也不会播 ——
而这种 bug 只有"第二张指令卡"才暴露。

**③ 淡入用 `CanvasGroup`** —— 卡面有十几张 `Image` + 若干段文字，
逐个改 alpha 既啰嗦又会漏；`CanvasGroup.alpha` 是整体乘算，一次搞定。
